# SealedSecret 계약 (빌드 체크리스트)

> 클러스터별로 kubeseal로 만들어야 할 Secret 목록 + **정확한 키명**. 차트마다 키명이 달라 통일 불가 — 이 표대로 만들어야 붙는다.
> 절차: sealed-secrets 컨트롤러 up(install.sh [5/9]) → 각 Secret을 `kubeseal`로 봉인 → 해당 네임스페이스에 SealedSecret 매니페스트 배치.
> 봉인 범위가 `strict`라 **이름과 네임스페이스에 묶인다.** 아래 소제목의 네임스페이스로 정확히 봉인해야 컨트롤러가 푼다.
> 만드는 주체 — `seal-secrets.sh`가 observability·data·app의 **10종을 일괄로**, 나머지 **7종은 낱개로**(generic은 `seal-one.sh`, dockerconfigjson은 kubectl 파이프라인) 만든다.
> 총 **17종**. `bootstrap/root-app.sh`의 `EXPECTED`가 이 수를 검사하므로 종수가 바뀌면 그 값도 같이 고친다.

### observability — 7종

⚠️ MinIO 3종(loki/mimir/tempo)은 **lgtm 전용 유저(minio-lgtm-user) 크레덴셜**을 각 차트가 요구하는 **다른 키명**으로 담는다(IAM 격리 — 루트 재사용 금지).

| Secret 이름 | 키(정확히) | 쓰는 곳 | 비고 |
|---|---|---|---|
| `minio-root-secret` | `rootUser`, `rootPassword` | MinIO 루트 | rootPassword 8자+ |
| `minio-lgtm-user` | `password` | MinIO lgtm 유저(IAM 격리) | 3버킷 한정 정책 lgtm-rw. 아래 S3 크레덴셜 3종의 출처 |
| `loki-s3-credentials` | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Loki S3 | AWS SDK 기본 체인 |
| `mimir-minio-credentials` | `MIMIR_S3_ACCESS_KEY_ID`, `MIMIR_S3_SECRET_ACCESS_KEY` | Mimir S3 | expand-env |
| `tempo-s3-credentials` | `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Tempo S3 | expand-env |
| `grafana-admin` | `admin-user`, `admin-password` | Grafana 관리자 | |
| `grafana-discord-webhook` | `DISCORD_WEBHOOK_URL` | Grafana 알림 발송 | **없으면 Grafana 가 `FailedMount` 로 기동하지 못한다** — 차트가 이 Secret 을 env 로 참조한다. Discord 채널 설정에서 웹훅을 만들어 그 URL 을 넣는다 |

### data — 2종

| Secret 이름 | 키(정확히) | 쓰는 곳 | 비고 |
|---|---|---|---|
| `mysql-secret` | `mysql-root-password`, **`mysql-password`** | MySQL 서버 루트 | **두 키 모두 필수·같은 값**. bitnami mysql 14.0.3은 `usePasswordFiles: true`(기본)라 `auth.username` 유무와 무관하게 두 키를 볼륨 items로 투영한다(실렌더 확인). 한 키만 넣으면 `couldn't find key mysql-password`로 파드가 ContainerCreating에서 멈춘다. ⚠️ `auth.username: root`는 금지 — 추가 유저 생성 칸이라 컨테이너가 "root user is already created"로 기동 거부(실행에서 확인). booking 은 `cgvapp` 계정으로 접속한다(전역 권한을 갖는 root 는 안 쓴다). `mysql-password` 가 그 계정의 비밀번호이고 booking-secrets 의 `MYSQL_PASSWORD` 와 **같은 값**이어야 한다. `mysql-root-password` 는 서버 루트라 다른 값이다 |
| `redis-secret` | `redis-password` | Redis auth (서버) | **dev HA도 필수**(Sentinel auth on). 클라 비번은 app ns로 복제 |

### app — 4종

app 파드는 data ns의 Secret을 직접 못 본다. 그래서 **같은 값을 app ns로 복제한다.**

| Secret 이름 | 키(정확히) | 쓰는 곳 | 비고 |
|---|---|---|---|
| `booking-secrets` | `MYSQL_PASSWORD`, `REDIS_PASSWORD` | booking DB·Redis 접속 | MYSQL_PASSWORD=mysql-secret 값 · REDIS_PASSWORD=redis-secret 값 |
| `queue-secrets` | `REDIS_PASSWORD` | queue Redis 접속 | = redis-secret 값. cgv-app은 envFrom만 지원→키명이 env명과 같아야 함 |
| `app-admin-token` | `ADMIN_TOKEN` | booking·queue 의 초기화 API 인증 · `demo-reset` CronJob | 값이 비어 있으면 그 컨트롤러가 등록되지 않아 초기화 경로 자체가 사라진다. 무작위 32자 이상 |
| `gitlab-registry` | `.dockerconfigjson` | 노드가 GitLab 레지스트리에서 이미지를 받아올 때 | **타입이 `kubernetes.io/dockerconfigjson`이라 `seal-one.sh`(generic 전용)로 못 만든다.** 아래 명령으로 만든다. 자격은 cgv-onprem 프로젝트의 deploy token(`read_registry`만 — 노드는 받아오기만 한다). `--docker-server`는 차트의 `image.repository` 앞부분과 **글자까지 같아야** kubelet이 매칭한다. 차트에서는 `cgv-app`의 `imagePullSecrets`가 이 이름을 가리킨다 |

```bash
kubectl create secret docker-registry gitlab-registry -n app \
  --docker-server=192.168.0.167:5050 \
  --docker-username='<deploy token 사용자명>' \
  --docker-password='<토큰>' \
  --dry-run=client -o yaml \
| kubeseal --format yaml \
    --controller-name sealed-secrets --controller-namespace kube-system \
> ../workloads/manifests/secrets/gitlab-registry.yaml
```

### argocd — 3종 (낱개 봉인)

앞의 10종과 달리 나중에 더해진 것이라 낱개로 만든다.

| Secret 이름 | 키(정확히) | 쓰는 곳 | 비고 |
|---|---|---|---|
| `argocd-repo-cgv-infra` | `type`, `url`, `username`, `password` | ArgoCD가 GitLab 저장소를 읽는 자격 **+ image updater가 태그를 되쓰는 자격(repocreds)** | `type=git`, `username`은 토큰 이름, `password`는 cgv-infra 프로젝트 access token(**`write_repository`, role Maintainer** — protected main의 push 예외가 Maintainers라서). **읽기·쓰기 통합인 이유**: updater의 전용 시크릿 경로(`git:secret:`)는 코드가 https 저장소만 받아 평문 http에서 `unknown repository type`으로 죽는다. repocreds 경로만 스킴을 안 가려, 저장소 자격 하나가 두 역할을 겸한다. **TLS 도입 때 read 전용 deploy token + 전용 write 시크릿으로 되돌린다.** `template.metadata.labels`에 `argocd.argoproj.io/secret-type: repository` 필수 |
| `argocd-secret` | `webhook.gitlab.secret` | GitLab이 보낸 webhook 요청의 발신자 확인 | **기존 Secret에 키 하나만 얹는다.** argo-cd 차트가 만들고 argocd-server가 `admin.password`·`admin.passwordMtime`·`server.secretkey`를 런타임에 써넣는 자리라, 통째로 대체하면 로그인과 세션 서명키를 잃는다. `template.metadata.annotations`의 `sealedsecrets.bitnami.com/patch: "true"`가 봉인본에 없는 키를 보존한다(v0.23.0+). 값은 임의의 난수를 만들어 GitLab 프로젝트 Webhooks의 **Secret token** 칸과 같게 넣는다(ArgoCD가 검사하는 것은 `X-Gitlab-Token` 헤더 하나라 GitLab의 Signing token은 쓸 수 없다). **아래 조건부의 수동 애노테이션이 선행돼야 한다** |
| `image-updater-registry` | `.dockerconfigjson` | image updater가 레지스트리에서 새 태그를 폴링하는 자격 | cgv-onprem deploy token(`read_registry`만). 노드 pull용 `gitlab-registry`(app ns)와 값 역할이 같지만 **주체(노드/봇)가 달라 가른다** — 유출 시 그것만 폐기. dockerconfigjson 타입이라 `seal-one.sh`(generic 전용)로 못 만들고 아래 명령으로 만든다. updater values의 `credentials: pullsecret:argocd/image-updater-registry`가 참조 |

```bash
./seal-one.sh argocd-repo-cgv-infra argocd argocd.argoproj.io/secret-type=repository
./seal-one.sh -a sealedsecrets.bitnami.com/patch=true argocd-secret argocd

kubectl create secret docker-registry image-updater-registry -n argocd \
  --docker-server=192.168.0.167:5050 \
  --docker-username='<deploy token 사용자명>' \
  --docker-password='<토큰>' \
  --dry-run=client -o yaml \
| kubeseal --format yaml \
    --controller-name sealed-secrets --controller-namespace kube-system \
> ../workloads/manifests/secrets/image-updater-registry.yaml
```

### cert-manager — 1종 (낱개 봉인)

| Secret 이름 | 키(정확히) | 쓰는 곳 | 비고 |
|---|---|---|---|
| `cloudflare-api-token` | `api-token` | `ClusterIssuer`의 DNS-01 solver가 Cloudflare DNS에 `_acme-challenge` TXT 레코드를 만들고 지우는 자격 | Cloudflare API 토큰(**Zone·DNS·Edit + Zone·Zone·Read**, `subinhong.dev` 한 존). Zone·Read가 같이 필요한 것은 solver가 레코드를 만들기 전에 도메인 이름으로 존 ID를 조회하기 때문이다. OPNsense DDNS가 쓰는 토큰과 **권한은 같지만 값을 따로 발급한다** — 한쪽이 유출돼도 그것만 폐기. 만료일·허용 IP는 걸지 않는다(집 공인 IP는 변동, 갱신은 90일마다 계속 돈다) |

`ClusterIssuer`는 클러스터 범위 오브젝트라 solver가 참조하는 Secret을 **cert-manager 네임스페이스에서만** 읽는다. 발급된 인증서 Secret은 이와 별개로 `Certificate`를 만든 네임스페이스(app)에 생긴다.

```bash
./seal-one.sh cloudflare-api-token cert-manager
#   키: api-token   값: Cloudflare API 토큰
```

**조건부:**
- **dev HA = Redis auth on** → queue도 `REDIS_PASSWORD`가 필요해 queue-secrets를 app ns에 둔다(envFrom).
- **mysql-secret 배달**: GitOps(sealed-secrets App wave -2)로 배달 → mysql App(wave -1)이 그 뒤 sync. 수동 apply 게이트 없음. root-app 전 봉인·커밋 선행 필수.
- **`argocd-repo-cgv-infra` 배달은 순환이다**: 이 Secret은 sealed-secrets App이 배달하는데, 그 App을 sync하려면 ArgoCD가 GitLab을 읽을 수 있어야 하고, 읽으려면 이 Secret이 필요하다. **재구축 시에는 `root-app.sh` 전에 이 한 장을 손으로 apply한다** — 컨트롤러가 이미 떠 있으므로(install.sh [5/9]) 그 자리에서 풀린다. 이후 GitOps가 같은 것을 관리한다.
  ```bash
  kubectl apply -f ../workloads/manifests/secrets/argocd-repo-cgv-infra.yaml
  ```
- **`root` Application도 같은 순환에 걸린다**: `bootstrap/root-app.yaml`이 `project: bootstrap`을 참조하는데, 그 AppProject를 만드는 매니페스트(`argocd/projects/bootstrap.yaml`)가 root가 관리하는 트리 안에 있다. ArgoCD는 참조한 AppProject가 없으면 Application을 sync하지 않으므로, **빈 클러스터에서는 root가 자기 프로젝트를 스스로 못 만들어 그 자리에서 멈춘다.** 지금 클러스터가 무증상인 것은 프로젝트를 전환할 때 순서가 우연히 맞았기 때문이다(살아 있던 root가 옛 프로젝트로 돌면서 새 프로젝트를 먼저 만들었다). `root-app.sh`가 root-app.yaml 직전에 이 한 장을 apply한다.
  ```bash
  kubectl apply -f ../argocd/projects/bootstrap.yaml
  ```
- **`argocd-secret`은 손으로 애노테이션을 한 번 붙여야 한다**: 컨트롤러는 `patch` 애노테이션을 봉인본이 아니라 **클러스터에 이미 있는 Secret에서 읽는다**(`isAnnotatedToBePatched(secret)`). 봉인본에만 적으면 `already exists and is not managed by SealedSecret`으로 거부한다. argo-cd 차트가 이 Secret을 먼저 만들므로, 봉인본을 배달하기 전에 한 번 붙인다. 통과한 뒤에는 봉인본의 애노테이션이 Secret에 남아 계속 통과한다.
  ```bash
  kubectl -n argocd annotate secret argocd-secret sealedsecrets.bitnami.com/patch=true
  ```
- **MinIO IAM 격리**: 루트 재사용 금지. lgtm 전용 유저(minio-lgtm-user, 정책 lgtm-rw = 3버킷 한정 CRUD)를 만들어 loki/mimir/tempo에 부여. negative test(타 버킷·admin API 거부)는 배포 후 mc로 확인.
- **`cloudflare-api-token` 배달에는 AppProject 확장이 선행된다**: 봉인본은 `sealed-secrets` App이 배달하고 그 App은 `secrets` 프로젝트에 묶여 있는데, 그 프로젝트의 `destinations`가 허용하는 네임스페이스만 대상이 된다. `cert-manager`가 거기 없으면 봉인본을 올려도 `destination namespace cert-manager is not permitted in project secrets`로 sync가 거부된다(`argocd/projects/secrets.yaml`).

## 서비스 DNS 정합 확인 (배포 후)
조사에서 일부 게이트웨이 서비스명이 버전/릴리스명 의존 — 배포 후 실제 이름으로 아래를 맞춰야 함:
- **Mimir 게이트웨이**: **`mimir-gateway`로 확정**(정합검증에서 helm template 렌더로 확인. `mimir-nginx`는 오기였음). grafana 데이터소스·alloy remote_write가 이걸 가리킴.
- **Loki 게이트웨이**: `loki-gateway`(기본 활성). 끄면 `loki:3100`.
- **Tempo**: HTTP 쿼리 `tempo:3200`, OTLP `tempo:4317/4318`.
- **prometheus-operator-crds**: Alloy가 **ServiceMonitor·PodMonitor CRD 둘 다** 필요(alloy 차트가 안 깖) → install.sh [6/9]가 둘 다 제공해야 함.
