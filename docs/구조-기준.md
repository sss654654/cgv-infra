# 저장소 구조와 기준

이 저장소는 ArgoCD가 읽는다. 브랜치는 `main` 하나이고, 환경은 `envs/` 폴더로 나눈다.
새 파일을 어디에 둘지 헷갈리면 이 문서의 기준으로 판단한다.

## 최상위 — 각 폴더가 답하는 질문

| 폴더 | 질문 | 누가 읽나 |
|---|---|---|
| `bootstrap/` | 빈 클러스터를 어떻게 세우나 | 사람 (한 번, 손으로) |
| `argocd/` | 무엇을 · 어디에 · 어떤 울타리 안에서 | ArgoCD |
| `charts/` | 배포물 — 값이 필요한 것 | ArgoCD (Helm 렌더) |
| `manifests/` | 배포물 — 정적인 것 | ArgoCD (그대로 apply) |
| `envs/` | 환경마다 얼마나 크게 | Helm (값으로만 참조) |
| `docs/` | 결정과 계약 | 사람 |

`envs/`는 배포되지 않는다. 어떤 Application도 `path`로 가리키지 않고, `valueFiles`로만 참조된다.

## 기준 여섯

### 1. Application인가 ApplicationSet인가

**반복되는 축이 있으면 ApplicationSet, 하나뿐이면 Application.**

축은 둘이다.
- **대상 축** — 같은 차트를 여러 이름에 (`cgv-app` 하나로 queue·booking·frontend)
- **환경 축** — 같은 것을 여러 환경에 (dev·stg)

둘 다 없으면(대상 하나 × 환경 하나) Application으로 손으로 쓴다.

### 2. 값을 어느 층에 적나

층이 답하는 질문이 다르다. 질문에 맞는 층에 적는다.

| 층 | 질문 | 예 |
|---|---|---|
| 차트 `values.yaml` | 이 차트의 기본값 | 렌더 기본 라벨, 기본 프로브 |
| 서비스 값 | 이 서비스가 무엇인가 | 포트, 프로브 경로, uid, PDB |
| `envs/<env>/` | 이 환경에서 얼마나 크게 | resources, 정원, 커넥션 풀, 이미지 태그 |

**환경이 바뀌어도 안 변하는 값은 환경 층에 두지 않는다.** 두면 환경이 늘 때마다 복제되고,
한쪽만 고치는 날이 온다.

한 값이 여러 축에 걸쳐 있으면 축마다 갈라서 적는다. 이미지가 그 예다.

| 부분 | 질문 | 사는 자리 | 쓰는 주체 |
|---|---|---|---|
| `image.registry` | 이 환경이 어디서 받아오나 | `argocd/applicationsets/apps.yaml`의 환경 목록 | 사람 |
| `image.repository` | 이 서비스가 무엇인가 | `charts/apps/<서비스>/values.yaml` | 사람 |
| `image.tag` | 어느 빌드인가 | `envs/<env>/<서비스>.yaml` | argocd-image-updater |

셋을 한 문자열로 두면 서비스 축과 환경 축이 한 값에 뭉쳐, 같은 주소가 두 층에 복제된다.

`registry`만 값 파일이 아니라 AppSet 환경 목록에 있다. image-updater가 폴링할 주소는
ApplicationSet이 애노테이션을 만들 때 정해지는데 그 시점에 Helm 값 파일은 아직 안 읽힌다 —
평가 주체가 다르다. 양쪽에 적으면 같은 주소가 두 곳에 생기므로, 목록을 정본으로 두고
렌더에는 `helm.parameters`로 내려보낸다. 그 줄 하나가 곧 환경의 정의다(`env` · `server` · `registry`).

argocd-image-updater는 이미지 이름 쓰기를 끌 수 없다 — `helm.image-name`을 비우거나 생략해도
기본값으로 쓴다. 그래서 그 자리를 템플릿이 읽지 않는 `imageUpdater.resolvedImage`로 돌렸다.
거기 쌓이는 값은 봇이 레지스트리에서 해석한 전체 주소이고 렌더에 쓰이지 않는다.

### 3. `charts/`인가 `manifests/`인가

**값으로 갈릴 여지가 있으면 `charts/`, 없으면 `manifests/`.**

지금 `manifests/`에 있는 것들은 환경이 하나뿐이라 값이 필요 없었다.
환경이 둘 이상이 되어 값이 갈려야 하면 차트로 옮긴다.

### 4. Application을 언제 합칠 수 있나

**`source` · `destination` · `project` · `sync-wave` 넷이 전부 같을 때만.**
하나라도 다르면 갈라야 한다. 특히 `destination.namespace`는 Application당 하나뿐이라 타협이 없다.

그래서 아래는 성격이 비슷해 보여도 합칠 수 없다.

| | 왜 못 합치나 |
|---|---|
| `cert-issuers` + `certificates` | 네임스페이스가 `cert-manager` / `app` |
| `netpol` + `netpol-app` | 네임스페이스가 `data` / `app`, 프로젝트도 다르다 |
| 관측 8종 | 업스트림 차트가 각각 달라 `source`가 하나로 안 모인다 |
| `metallb` + `metallb-pool` | 컨트롤러(CRD)와 CR을 한 sync에 넣으면 초기 배포가 불안정하다 |

**ApplicationSet은 Application을 합치지 않는다.** 개수는 그대로 두고 찍어내는 틀만 공유한다.
목록 항목마다 `project`와 `namespace`를 다르게 줄 수 있으므로,
위처럼 합칠 수 없는 것들도 AppSet 하나가 각각 만들 수 있다.
**줄어드는 것은 Application 수가 아니라 사람이 쓰는 파일 수다.**

### 5. AppProject를 무엇 단위로 나누나

**울타리 내용이 실제로 다른 단위로만 나눈다.**

`sourceRepos` · `destinations` · `clusterResourceWhitelist` · `namespaceResourceWhitelist`
넷 중 하나라도 다르면 나눌 값이 있고, 넷이 같으면 나눠도 파일만 는다.

앱 워크로드에 리소스 종류를 나열하지 않는 것은 의도다.
차트에 리소스가 하나 늘 때마다 프로젝트를 고쳐야 하므로, 네임스페이스와 cluster-scoped 금지로 막는다.

### 6. 이름

- **같은 이름이 층을 관통한다** — `queue`는 `charts/apps/queue/`, `envs/dev/queue.yaml`.
  `values-queue.yaml` 같은 접두어를 붙이지 않는다. 폴더가 이미 그 역할을 말한다.
- **도메인 이름이 세 곳에서 같다** — AppProject `data` = 네임스페이스 `data`.
- **폴더는 ArgoCD CRD 종류 그대로** — `applications` · `applicationsets` · `projects`.
  ArgoCD를 아는 사람이 설명 없이 읽는다.
- **사적 이름을 쓰지 않는다** — 장소나 소유를 가리키는 이름 대신 역할과 기술 이름으로.

## 값이 쌓이는 순서

`valueFiles`는 나중에 오는 파일이 이긴다. 없는 키는 앞 층 값이 남는다.

```
1  charts/<차트>/values.yaml          차트 기본값
2  charts/apps/<서비스>/values.yaml   이 서비스가 무엇인가        (apps AppSet 만)
3  envs/<env>/<서비스>.yaml           이 환경에서 얼마나 크게
4  helm.parameters                    AppSet 환경 목록이 주는 값 (image.registry)
```

경로 표기가 두 가지인 것은 상황이 둘이기 때문이지 규칙이 둘이어서가 아니다.

| 차트가 어디 있나 | 값 경로 | 왜 |
|---|---|---|
| 이 저장소 안 (`apps` · `data`) | `../../../envs/...` — `source.path` 기준 | 소스가 하나라 상대 경로로 닿는다 |
| 업스트림 (`platform` · `observability`) | `$values/charts/...` — 저장소 루트 기준 | 차트 소스가 git이 아니라, 값 제공용 git 소스를 따로 두고 `ref: values`로 가리킨다 |

## 환경

| env | 클러스터 | 상태 |
|---|---|---|
| `dev` | 온프레미스 k3s | 활성 |
| `stg` | (미정) | 값 골격만. 배포 배선 없음 |

`prd`는 만들지 않는다. 대상 클러스터가 생길 때 `envs/prd/`를 신설한다.
아무도 참조하지 않는 폴더를 미리 두지 않는다.

## 아직 기준대로 되어 있지 않은 것

이 문서의 기준과 현재 코드가 어긋나는 지점이다. 순서대로 해소한다.

1. **환경 축이 `apps`와 `data`에만 있다** — 두 AppSet은 환경 목록에 한 줄을 더하면 클러스터가
   늘어난다. `manifests` AppSet과 개별 Application 8개는 아직 `destination.server`가 리터럴이다.
   stg를 붙일 때 어떤 매니페스트가 환경별 경로를 필요로 하는지(봉인 키가 다른 `secrets`,
   도메인이 다른 `certificates`)가 정해지므로, 그때 축을 건다.
2. **`charts/apps/<서비스>/`에 차트가 없다** — `values.yaml` 하나뿐인데 `charts/` 아래 있다.
   디렉터리 순회 제너레이터는 없앴지만 폴더 배치는 그대로다. 값 전용 자리로 옮길지 정해야 한다.
3. **환경 축이 워크로드 넷에만 있다** — 관측 8종과 `manifests/` 아래 것들은 값으로 갈릴 자리가 없다.
   특히 `kafka`는 브로커 수가 CR에 박혀 있어 환경마다 못 바꾼다. 차트로 만들면 `data` AppSet으로 옮긴다.
4. **Application 이름에 환경이 없다** — `queue`·`redis`처럼 접미사가 없어, 환경이 둘이 되면
   한쪽만 `-stg`가 붙는 비대칭이 생긴다. 이름 변경은 Application이 지워졌다 다시 만들어지는 일이라
   구조 변경과 섞지 않고 따로 한다.
5. **`clusterResourceWhitelist: []`가 `data` 프로젝트에서 검증되지 않았다** — 미들웨어가
   cluster 범위 리소스를 안 만든다는 판단으로 닫았다. 틀렸으면 ArgoCD가
   "resource not permitted in project"로 명시적으로 실패하므로 조용히 넘어가지는 않는다.
