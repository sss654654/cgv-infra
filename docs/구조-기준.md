# cgv-infra 저장소 구조

이 저장소는 홈랩 k3s 클러스터의 상태를 선언으로 갖고 있고, ArgoCD 가 그것을 읽어 클러스터를 그 상태로 맞춘다.
브랜치는 `main` 하나이고 환경은 `envs/` 폴더로 나눈다.

새 파일을 어디에 둘지, 무엇을 하나로 합칠지 판단할 때 이 문서를 본다.

---

## 이 저장소가 어떻게 흘러가나

세 문장이 전부다.

1. 사람이든 봇이든 `main` 에 push 하면 ArgoCD 가 읽어 클러스터를 그 상태로 맞추고, 그 뒤로도 계속 맞춘다.
2. Application 마다 차트나 매니페스트를 가리키고, 차트는 환경별 값으로 렌더된 다음 적용된다.
3. 봇(argocd-image-updater)이 push 하는 것은 이미지 태그 한 줄뿐이다.

### 시작점 — 손으로 하는 것은 한 번뿐이다

```
kubectl apply -f bootstrap/root-app.yaml
```

이 한 번으로 나머지가 딸려 온다. `root` Application 이 `argocd/` 폴더 전체를 읽기 때문이다.

```yaml
source:
  path: argocd
  directory:
    recurse: true
syncPolicy:
  automated: { prune: true, selfHeal: true }
```

`argocd/` 안에는 선언 21개가 있고, 그중 ApplicationSet 5개가 다시 Application 을 찍어낸다.

| 무엇 | 개수 |
|---|---|
| `argocd/projects/` AppProject | 8 |
| `argocd/applications/` Application | 11 |
| `argocd/applicationsets/` ApplicationSet | 5 |
| 그 5개가 만드는 Application (3 + 1 + 4 + 8 + 1) | 17 |
| `root` 자신 | 1 |
| **클러스터의 Application 합계** | **29** |

`bootstrap/root-app.yaml` 은 `argocd/` **밖에** 있다. root 가 자기 자신을 배달하지 않으므로,
이 파일을 고치면 `kubectl apply -f bootstrap/root-app.yaml` 로 직접 갱신해야 반영된다.

root 가 `prune: true` 라서 `argocd/` 에서 파일을 지우는 커밋 하나로 그 객체가 사라진다.
ApplicationSet 의 기본 삭제 동작은 cascade 이므로, AppSet 파일 하나를 지우면 그것이 만든
Application 이 워크로드째 사라진다. `argocd/applicationsets/observability.yaml` 의
`preserveResourcesOnDeletion: true` 가 그 반경을 "관리만 이탈, 리소스는 존치"로 맞춘다.

## 1. 최상위 폴더 — 각 폴더가 답하는 질문

| 폴더 | 질문 | 누가 읽나 |
|---|---|---|
| `bootstrap/` | 빈 클러스터를 어떻게 세우나 | 사람 (한 번, 손으로) |
| `argocd/` | 무엇을 · 어디에 · 어떤 울타리 안에서 | ArgoCD |
| `charts/` | 배포물 — 값이 필요한 것 | ArgoCD (Helm 렌더) |
| `manifests/` | 배포물 — 정적인 것 | ArgoCD (그대로 apply) |
| `envs/` | 이 환경에서 얼마나 크게 | Helm (값으로만 참조) |
| `schemas/` | CI 가 CRD 를 검증할 스키마 | GitLab CI (kubeconform) |
| `docs/` | 결정과 계약 | 사람 |

세 폴더가 성격으로 갈린다.

| 폴더 | 클러스터에 올라가나 | 렌더를 거치나 |
|---|---|---|
| `charts/` | 올라간다 | 거친다 |
| `manifests/` | 올라간다 | 안 거친다 (YAML 그대로 apply) |
| `envs/` | **올라가지 않는다** | 렌더의 재료로만 읽힌다 |

어떤 Application 도 `envs/` 를 `path` 로 가리키지 않는다. `valueFiles` 로만 참조된다.

`manifests/` 에 렌더가 없는 이유는 값이 필요 없어서다. SealedSecret · ClusterIssuer ·
Middleware 는 환경마다 달라질 값이 없다.

**환경이 갈리는 자리는 `envs/<환경>/` 안의 파일뿐이다.** 그래서 `manifests/` 아래에는 환경 이름이
들어간 경로가 없고, 환경마다 달라지는 것은 정적 매니페스트로 둘 수 없다 — 값을 받을 자리가
없어서다. NetworkPolicy 가 2026-09-11 에 그 이유로 `charts/platform/netpol` 로 옮겨졌다.
stg 는 입구가 ALB 이고 MySQL·Redis 가 관리형이라 정책이 가리키는 대상이 통째로 다른데,
같은 파일에 두 답을 담을 수가 없었다.

## 2. 차트가 클러스터 객체가 되기까지

두 단계이고 이름이 다르다.

```
렌더링   차트 + 값  →  YAML          helm template 이 하는 것
적용     YAML       →  클러스터 객체   ArgoCD sync 가 하는 것
```

ArgoCD 가 Application 하나에서 하는 렌더링은 이 한 줄로 환원된다.

```
helm template <releaseName> <source.path> -f <valueFiles 1> -f <valueFiles 2> ...
```

`queue-dev` Application 을 예로 풀면 이렇게 된다.

```yaml
path: charts/apps/cgv-app          # 어느 폴더를 볼지. Chart.yaml 이 있으면 Helm 차트로 읽는다
helm:
  releaseName: queue
  valueFiles:
    - values.yaml                       # charts/apps/cgv-app/values.yaml
    - '../queue.yaml'                   # charts/apps/queue.yaml
    - '../../../envs/dev/queue.yaml'    # envs/dev/queue.yaml
```

```
helm template queue charts/apps/cgv-app \
  -f charts/apps/cgv-app/values.yaml \
  -f charts/apps/queue.yaml \
  -f envs/dev/queue.yaml
```

- `valueFiles` 의 상대 경로 기준은 `source.path` 다. `charts/apps/cgv-app` 에서 `../../../` 는 저장소 루트다.
- 값 파일은 **나중에 오는 것이 앞을 덮는다.** 없는 키는 앞 층 값이 남는다.

### 한 번의 렌더가 객체 여러 개를 만든다

`charts/apps/cgv-app/templates/` 에 템플릿이 9장 있고, `deployment.yaml` 만 조건이 없다.
나머지는 값으로 켜고 끈다.

| 템플릿 | 조건 |
|---|---|
| `deployment.yaml` | 없음 — 항상 나온다 |
| `service.yaml` | `service.enabled` |
| `ingress.yaml` | `ingress.enabled` |
| `hpa.yaml` | `autoscaling.enabled` |
| `pdb.yaml` | `podDisruptionBudget.enabled` |
| `podmonitor.yaml` | `metrics.enabled` and `metrics.kind == "PodMonitor"` |
| `servicemonitor.yaml` | `metrics.enabled` and `metrics.kind == "ServiceMonitor"` |
| `serviceaccount.yaml` | `serviceAccount.create` |
| `migration-job.yaml` | `migration.enabled` |

같은 차트인데 서비스마다 나오는 객체가 다르다. queue 는 PodMonitor 가 나오고 booking 은
ServiceMonitor 가 나온다 — 값에서 `metrics.kind` 만 다르다.

### 렌더 결과는 저장소에 남기지 않는다

저장소에 있는 것은 차트와 값이고, 렌더된 YAML 은 ArgoCD 안에서 만들어져 바로 적용된다.
CI 가 검증용으로 만드는 `rendered/` 는 `.gitignore` 에 있다. 산출물이 커밋되면 저장소의
차트·값과 갈라져도 드러나지 않는다.

## 3. 값을 어느 층에 적나

값을 가르는 축이 둘이다 — **어느 서비스인가**와 **어느 환경인가**. 층이 답하는 질문이 다르므로
질문에 맞는 층에 적는다.

| 순서 | 층 | 질문 | 예 |
|---|---|---|---|
| 1 | `charts/<차트>/values.yaml` | 이 차트의 기본값 | 렌더 기본 라벨, 기본 프로브 |
| 2 | `charts/<카테고리>/<이름>.yaml` | 이것이 무엇인가 (환경 무관) | 포트, 프로브 경로, uid, `image.repository`, 자원 |
| 3 | `envs/<env>/[<카테고리>/]<이름>.yaml` | 이 환경에서 얼마나 크게 · 무엇에 붙나 | resources, 정원, 커넥션 풀, `image.tag`, 저장소 주소 |
| 4 | `helm.parameters` | 두 시점에 동시에 필요한 것 | `image.registry` |

환경이 바뀌어도 안 변하는 값은 환경 층에 두지 않는다. 두면 환경이 늘 때마다 복제되고,
한쪽만 고치는 날이 온다.

**3층이 답하는 질문이 둘이다.** "얼마나 크게" 만이 아니라 "무엇에 붙나" 도 여기 있다 —
`envs/dev/booking.yaml` 의 `MYSQL_HOST`, `envs/dev/frontend.yaml` 의 `DNS_RESOLVER`,
`envs/dev/netpol.yaml` 의 정책 대상이 그렇다. 같은 질문의 답이 두 폴더로 갈리면
하나를 고칠 때 다른 하나를 놓친다.

**관측은 한 단계 더 들어간다** — `envs/<env>/observability/<이름>.yaml`.
컴포넌트가 여덟이라 `envs/<env>/` 바로 아래 두면 앱 값과 섞인다.

### 이미지가 세 축으로 갈린 이유

한 값이 여러 축에 걸쳐 있으면 축마다 갈라서 적는다.

| 부분 | 질문 | 사는 자리 | 쓰는 주체 |
|---|---|---|---|
| `image.registry` | 이 환경이 어디서 받아오나 | `argocd/applicationsets/apps.yaml` 의 환경 목록 | 사람 |
| `image.repository` | 이 서비스가 무엇인가 | `charts/apps/<서비스>/values.yaml` | 사람 |
| `image.tag` | 어느 빌드인가 | `envs/<env>/<서비스>.yaml` | argocd-image-updater |

셋을 한 문자열로 두면 서비스 축과 환경 축이 한 값에 뭉쳐, 같은 주소가 두 층에 복제된다.

### `registry` 만 값 파일 밖에 있는 이유 — 평가 시점이 둘이다

```
시점 1   ApplicationSet 이 Application 을 만든다      애노테이션이 문자열로 굳는다
시점 2   ArgoCD 가 sync 하며 Helm 을 렌더한다         valueFiles 가 읽힌다
```

argocd-image-updater 는 Application 의 애노테이션만 읽는다. 그 애노테이션은 시점 1에 정해지는데,
`envs/<env>/<서비스>.yaml` 은 그때 아직 읽히지 않는다. 레지스트리 주소를 값 파일에만 두면
애노테이션에는 같은 주소를 따로 적어야 하고, 둘이 갈라지면 봇이 감시하는 레지스트리와
파드가 받아오는 레지스트리가 달라진다. 그 어긋남은 ArgoCD 화면에 안 나타난다.

그래서 환경 목록 한 줄을 정본으로 두고 두 곳에 내려보낸다.

```yaml
- { env: dev, server: "https://kubernetes.default.svc", registry: "192.168.0.167:5050" }
        │
        ├─ annotations       image-list: app={{.registry}}/{{.image}}     봇이 폴링할 주소
        └─ helm.parameters   image.registry={{.registry}}                 파드가 받아올 주소
```

`valueFiles` 가 아니라 `helm.parameters` 인 이유는 `valueFiles` 가 파일 이름 목록이라
ApplicationSet 이 그 안에 값을 넣을 수 없기 때문이다. `parameters` 는 `helm --set` 과 같아서
생성 시점에 만든 문자열을 그대로 넘긴다.

그 줄 하나가 곧 환경의 정의다 — `env` · `server` · `registry`.

### 값 경로 표기가 두 가지인 이유

규칙이 둘이어서가 아니라 차트가 사는 곳이 둘이어서다.

| 차트가 어디 있나 | 값 경로 | 왜 |
|---|---|---|
| 이 저장소 안 (`apps` · `data`) | `../../../envs/...` — `source.path` 기준 | 소스가 하나라 상대 경로로 닿는다 |
| 업스트림 (`platform` · `observability`) | `$values/charts/...` — 저장소 루트 기준 | 차트 소스가 git 이 아니라, 값 제공용 git 소스를 따로 두고 `ref: values` 로 가리킨다 |

## 4. `charts/` 안에 있는 세 종류

**폴더는 차트, 파일은 값.** `charts/` 아래에서 폴더를 세면 그게 차트 수다(5개).

| 종류 | 개수 | 무엇이 들어 있나 | 어느 것 |
|---|---|---|---|
| 직접 만든 차트 | 3 | `Chart.yaml` + `templates/` | `charts/apps/cgv-app` (10장) · `charts/platform/netpol` (4장) · `charts/data/cgv-kafka` (2장) |
| 래퍼 차트 (vendoring) | 2 | `Chart.yaml` + `dependencies` + `charts/*.tgz` | `charts/data/cgv-mysql` · `cgv-redis` |
| 값 파일 | 14 | 그 이름의 차트에 먹이는 환경 무관 값 | `charts/observability/*.yaml` (8) · `charts/platform/*.yaml` (3) · `charts/apps/*.yaml` (3) |

2026-09-11 에 값만 있던 폴더 열넷을 파일로 폈다. 전에는 폴더 19개 중 차트가 5개라 열어 봐야
어느 쪽인지 알 수 있었다. `charts/observability/` 에는 차트가 하나도 없다 — 여덟 다 업스트림이라
저장소에는 값만 있다.

`netpol` 과 `cgv-kafka` 는 전에 `manifests/` 에 있었다. 차트가 된 이유는 종류가 아니라
**환경마다 값이 달라서** 다 — 값을 받을 자리가 필요해졌다. 정적 매니페스트에는 그 자리가 없다.

값 파일만 있는 14개도 두 종류다.

| 무엇에 먹이는 값인가 | 개수 | 어느 것 |
|---|---|---|
| 이 저장소의 `cgv-app` 차트 | 3 | `charts/apps/{queue,booking,frontend}` |
| 업스트림 차트 | 11 | `charts/observability/*` (8) · `charts/platform/*` (3) |

`charts/observability/grafana/` 에는 값만 있고 grafana 차트 본체는 이 저장소에 없다.
ArgoCD 가 sync 할 때 `https://grafana.github.io/helm-charts` 에서 받아온다.

### 업스트림 차트를 받는 방식

셋이 있고 지금 둘이 섞여 있다.

| 방식 | 차트가 어디서 오나 | 저장소에 무엇이 남나 |
|---|---|---|
| A — 업스트림 직접 | 배포할 때마다 업스트림 저장소에서 | 값 파일만 |
| B — vendoring | 저장소 안의 `.tgz` | `.tgz` + `Chart.lock` + 값 |
| C — 사내 레지스트리 | GitLab OCI 레지스트리에서 | 값 파일만 |

**지금 규칙 — bitnami 계열은 B, 나머지는 A + `targetRevision` 고정.**

`cgv-mysql` 과 `cgv-redis` 만 vendoring 인 이유는 bitnami 가 2025 년에 이미지 태그를 대량
삭제한 사건이다. vendoring 의 값은 수정 가능성이 아니라 **공급이 끊겨도 배포가 되는 것**이다.
래퍼는 업스트림을 `dependencies` 로 거는 구조라 템플릿 자체는 고칠 수 없다.

저장소 무게는 판단 근거가 되지 않는다.

| | 크기 |
|---|---|
| `charts/data/cgv-mysql/charts/mysql-14.0.3.tgz` | 69 KB |
| `charts/data/cgv-redis/charts/redis-27.0.15.tgz` | 106 KB |
| 저장소 전체 (`git count-objects`) | 1.84 MB |

**목표는 C 로 통일하는 것이고, 실행은 EKS 사이클 뒤다.** 근거는 셋이다.

- 차트는 홈랩 ArgoCD 가 받는다. EKS 노드가 받는 것은 이미지다. 차트 소스는 EKS 작업의 선행 조건이 아니다.
- GitLab 레지스트리가 이미 있고, CI 도구 이미지(helm · kubeconform)가 이미 거기에 있다.
- B 에서 C 로 가는 것은 되돌리기가 아니라 `.tgz` 를 push 하는 승격이다.

C 로 갈 때 확인해야 할 것: 평문 http 레지스트리에 ArgoCD 의 OCI 지원(`enableOCI` + `insecure`)이 붙는가.

## 5. Application 인가 ApplicationSet 인가

**반복되는 축이 있으면 ApplicationSet, 하나뿐이면 Application.**

축은 둘이다.

- **대상 축** — 같은 차트를 여러 이름에 (`cgv-app` 하나로 queue · booking · frontend)
- **환경 축** — 같은 것을 여러 환경에 (dev · stg)

판단 기준은 **지금 몇 개인가가 아니라 곱해질 축이 있는가**다. `redis` 와 `traefik` 은 지금
원소가 하나뿐인데도 ApplicationSet 이다. 환경 축이 있어서 stg 가 생기면 둘이 된다.

조건 둘의 역할이 다르다.

```
틀이 같다   ApplicationSet 으로 낼 수 "있다"      가능 조건
축이 있다   ApplicationSet 으로 내는 것이 맞다     선택 이유
```

`metallb` 가 그 구분의 사례다. metallb 는 traefik 과 틀이 같아서(업스트림 차트 + git values)
원래 platform ApplicationSet 안에 있었다. 클라우드에서는 관리형 로드밸런서가 그 자리를 대신하므로
metallb 에는 환경 축이 없고, matrix 는 모든 원소를 모든 환경에 곱하므로 한 AppSet 에 두면
metallb 까지 stg 에 생긴다. 그래서 개별 Application 으로 갈랐다.

### matrix 는 곱셈이다

| ApplicationSet | 대상 축 | 환경 축 | 지금 | stg 를 넣으면 |
|---|---|---|---|---|
| `apps` | 3 (queue · booking · frontend) | 1 | 3 | 6 |
| `data` | 1 (redis) | 1 | 1 | 2 |
| `manifests` | 8 (경로) | 1 | 8 | 16 |
| `platform` | 1 (traefik) | 1 | 1 | 2 |
| `observability` | 8 (컴포넌트) | 없음 | 8 | 8 |

`observability` 만 환경 축이 없다. stg 의 관측을 어떻게 붙일지가 아직 정해지지 않았다.

`observability` 원소 8개는 저장소가 네 곳(grafana · grafana-community · min.io ·
prometheus-community)으로 갈리는데도 한 AppSet 이다. ApplicationSet 이 요구하는 것은
값이 같은 것이 아니라 **틀이 같은 것**이다. 여덟이 전부 "업스트림 차트 + git values" 라는
같은 모양이고, 달라지는 좌표(`repoURL` · `chart` · `version` · `namespace`)는 원소로 뺐다.

### ApplicationSet 은 Application 을 합치지 않는다

개수는 그대로 두고 찍어내는 틀만 공유한다. 원소 8개면 Application 8개가 각각 생기고,
각자 자기 Synced/Healthy 를 갖고 따로 sync 된다.

**줄어드는 것은 Application 수가 아니라 사람이 쓰는 파일 수다.** 구조를 재편했을 때
파일은 25개에서 20개가 됐고 Application 은 30개에서 31개가 됐다.

Application 을 합치면 sync 단위가 뭉개진다. 관측 8개를 하나로 합치면 grafana 하나가 실패했을 때
loki · mimir · tempo 까지 같은 Application 안에서 실패로 보인다.

### 언제 합칠 수 있나

**`source` · `destination` · `project` · `sync-wave` 넷이 전부 같을 때만.** 하나라도 다르면 갈라야 한다.

`destination.namespace` 는 **네임스페이스를 안 적은 리소스의 기본값**이다. 매니페스트가
`metadata.namespace` 를 명시하면 그 리소스는 거기로 간다. 그것을 막는 것은 AppProject 의
`destinations` 다. Application 하나가 여러 네임스페이스에 배포하는 것은 가능하고,
**프로젝트가 그 네임스페이스를 전부 허용할 때만** 성립한다.

- `sealed-secrets` 가 그 예다. 봉인본 17개가 다섯 네임스페이스에 각자 `namespace:` 를 명시하고,
  `secrets` 프로젝트가 다섯을 다 허용한다. 하나로 두는 이유는 종류가 SealedSecret 하나뿐이라
  프로젝트를 좁게 유지할 수 있어서다.
- `netpol` 이 갈린 이유는 반대다. `infra` 프로젝트가 `data` 와 `platform` 으로 쪼개지며
  프로젝트 하나가 한 네임스페이스만 허용하게 됐고, 두 네임스페이스에 걸쳐 있던
  Application 의 한쪽이 거부되며 OutOfSync 로 드러났다. Application 이 30개에서 31개가 된 것은
  그 하나를 푼 결과다.

**규칙은 "네임스페이스 하나"가 아니라 "프로젝트 울타리 안"이다.** 울타리를 좁힐수록
Application 도 그 단위로 갈린다.

아래는 성격이 비슷해 보여도 합칠 수 없다.

| | 왜 못 합치나 |
|---|---|
| `cert-issuers` + `certificates` | 네임스페이스가 `cert-manager` / `app` |
| `netpol-data` + `netpol-app` | 네임스페이스가 `data` / `app`, 프로젝트도 다르다 |
| 관측 8종 | 업스트림 차트가 각각 달라 `source` 가 하나로 안 모인다 |
| `metallb` + `metallb-pool` | 컨트롤러(CRD)와 CR 을 한 sync 에 넣으면 초기 배포가 불안정하다 |

ApplicationSet 은 원소마다 `project` 와 `namespace` 를 다르게 줄 수 있으므로,
위처럼 합칠 수 없는 것들도 AppSet 하나가 각각 만든다. `manifests` AppSet 이 그렇게 동작한다.

## 6. AppProject — 무엇을 할 수 있는지의 울타리

Application 은 `spec.project` 에 프로젝트 이름을 적어 울타리를 고른다. 적지 않으면 `default` 로
가고, `default` 는 저장소 · 네임스페이스 · 리소스가 전부 열려 있다.

AppProject 가 가진 것은 넷이다.

| 필드 | 무엇을 정하나 |
|---|---|
| `sourceRepos` | 어느 저장소에서 읽을 수 있나 |
| `destinations` | 어느 클러스터의 어느 네임스페이스에 배포할 수 있나 |
| `clusterResourceWhitelist` | 클러스터 범위 리소스 중 어떤 종류를 만들 수 있나 |
| `namespaceResourceWhitelist` | 네임스페이스 범위 리소스 중 어떤 종류를 만들 수 있나 |

### 범위가 둘이라 목록도 둘이다

쿠버네티스 리소스는 네임스페이스 범위와 클러스터 범위로 갈린다. 이 클러스터 기준으로
클러스터 범위가 84종, 네임스페이스 범위가 111종이다(`kubectl api-resources --namespaced=false`).

| 범위 | 예 |
|---|---|
| 네임스페이스 | Pod · Deployment · Service · Secret · PVC · NetworkPolicy · Role · SealedSecret · IPAddressPool · Middleware · ServiceMonitor |
| 클러스터 | Namespace · Node · PersistentVolume · StorageClass · CRD · ClusterRole · ClusterRoleBinding · ClusterIssuer |

`destinations` 는 네임스페이스 범위 리소스에만 의미가 있다. 클러스터 범위 리소스에는
네임스페이스라는 필드가 없어서 `destinations` 를 아무리 좁혀도 걸리지 않는다.
그래서 그것을 막는 문이 `clusterResourceWhitelist` 로 따로 있다.

`ClusterRole` 은 그 84종 중 하나일 뿐이고, `clusterResourceWhitelist` 와 RBAC 은 관계가 없다.
두 목록이 나열하는 것은 권한 규칙이 아니라 **만들어도 되는 리소스 종류**다.

### 무엇을 막고 무엇을 못 막나

| | |
|---|---|
| 막는다 | 값이나 차트 때문에 다른 네임스페이스에 객체가 생기는 것 |
| | 차트가 만드는 cluster 범위 리소스 |
| | 의도하지 않은 업스트림 저장소에서 읽는 것 |
| 못 막는다 | 저장소에 쓰기 권한이 있는 사람이 `spec.project` 를 바꾸는 것 |

넘으면 조용히 통과하지 않고 `resource not permitted in project` 또는
`application destination ... is not permitted in project` 로 명시적으로 실패한다.

손으로 배포할 때는 `kubectl` 을 치는 사람의 RBAC 이 울타리였다. ArgoCD 는 클러스터 관리자급
권한으로 커밋을 그대로 옮기므로, 그 자리를 이 선언이 대신한다.

### 지금 있는 7개

| 프로젝트 | 어디에 (destinations) | 클러스터 범위 | 네임스페이스 범위 |
|---|---|---|---|
| `bootstrap` | argocd | 없음 | AppProject · Application · ApplicationSet 셋만 |
| `argocd` | argocd | 전부 | 전부 |
| `apps` | app | 없음 | 전부 |
| `data` | data | 없음 | 전부 |
| `platform` | observability · observability-host · metallb-system · traefik | 전부 | 전부 |
| `secrets` | data · app · observability · argocd · cert-manager | 없음 | SealedSecret 하나만 |
| `cert` | cert-manager | ClusterIssuer 하나만 | 없음 |

- `bootstrap` 은 root Application 전용이다. GitOps 진입점이 `default`(전권)에 있으면
  클러스터에서 가장 넓은 권한을 갖게 되는데, 실제로 만드는 것은 `argocd/` 아래의 선언 3종뿐이다.
- `argocd` 는 양쪽이 다 열려 있다. argo-cd 차트가 CRD · ClusterRole · ClusterRoleBinding 을
  만든다. 대신 네임스페이스가 하나다.
- `apps` 와 `data` 는 네임스페이스 하나 + 클러스터 범위 금지. 워크로드 프로젝트의 기본형이다.
- `platform` 은 가장 넓다. 업스트림 차트들이 CRD 와 ClusterRole 을 만든다.
- `secrets` 는 네임스페이스가 다섯이고 종류가 하나다. Secret 은 그것을 쓰는 파드와 같은
  네임스페이스에 있어야 하므로 넓힐 수밖에 없고, 대신 종류를 하나로 고정했다.
- `cert` 는 종류 하나에 네임스페이스 범위는 0 이다.

### 무엇 단위로 나누나

**울타리 내용이 실제로 다른 단위로만 나눈다.** 위 네 필드 중 하나라도 달라지면 나눌 값이 있고,
넷이 같으면 나눠도 파일만 는다.

울타리를 합치면 그 내용이 합집합이 된다. 가장 넓은 것에 맞춰지므로, 좁은 쪽이 필요 없는
권한까지 갖게 된다.

- `infra` 하나였을 때 traefik Application 이 `data` 네임스페이스에 무엇이든 만들 수 있었다.
  `data` 로 갈라내며 `clusterResourceWhitelist: []` 가 생겼다.
- `cert` 를 따로 둔 이유가 같다. ClusterIssuer 하나를 만들자고 `platform` 의 `destinations` 에
  `cert-manager` 를 열면, 화이트리스트가 `*/*` 라 platform 소속 Application 전부에게
  그 네임스페이스가 열린다.

### 리소스 종류를 언제 못 박나

**그 Application 이 만드는 종류가 고정되어 있으면 나열하고, 자라는 곳이면 열어 둔다.**

| | 종류 | 왜 |
|---|---|---|
| `secrets` · `cert` | 나열한다 | 배달 전용이라 종류가 늘지 않는다 |
| `bootstrap` | 나열한다 | root 가 만드는 것은 argoproj.io 3종으로 고정이다 |
| `apps` · `data` · `platform` · `argocd` | `*` 로 연다 | 차트에 리소스가 하나 늘 때마다 프로젝트를 고쳐야 한다 |

`apps` 와 `data` 에서 막는 것은 종류가 아니라 네임스페이스와 cluster 범위 금지다.

### 지금 쓰지 않는 것

| 필드 | 무엇을 하나 | 왜 안 쓰나 |
|---|---|---|
| `roles` | 이 프로젝트를 누가 sync · delete 할 수 있나 | ArgoCD 사용자가 하나다 |
| `syncWindows` | 배포 가능 · 금지 시간대 | 배포 시각을 제한할 이유가 아직 없다 |
| `*Blacklist` | "이것만 빼고 전부" | 화이트리스트가 기본 거부라 더 좁다 |

AppProject 는 원래 여러 팀이 한 ArgoCD 를 공유할 때 서로를 격리하는 장치다. 이 저장소는
사용자가 하나여서 그 축이 없고, 사고 반경을 좁히는 쪽으로만 쓴다.

## 7. 이름

- **같은 이름이 층을 관통한다** — `queue` 는 `charts/apps/queue/`, `envs/dev/queue.yaml`.
  `values-queue.yaml` 같은 접두어를 붙이지 않는다. 폴더가 이미 그 역할을 말한다.
- **Application 이름의 환경 접미사는 환경 축이 있는 것에만 붙인다** — `queue-dev` · `traefik-dev`.
  `metallb` · `mysql` · `dashboards` · 관측 8종은 온프레미스에만 있으므로 접미사가 없다.
  이름만 보고 "환경마다 있는 것 / 한 곳에만 있는 것"이 구분된다.
  파일 이름에는 안 붙는다 — 접미사는 ApplicationSet 이 생성할 때만 만들어진다.
- **Helm 릴리스 이름은 접미사 없이 고정한다** — `releaseName: '{{.name}}'`.
- **도메인 이름이 세 곳에서 같다** — AppProject `data` = 네임스페이스 `data`.
- **폴더는 ArgoCD CRD 종류 그대로** — `applications` · `applicationsets` · `projects`.
- **사적 이름을 쓰지 않는다** — 장소나 소유를 가리키는 이름 대신 역할과 기술 이름으로.

### 릴리스 이름을 고정하는 이유

ArgoCD 는 Helm 릴리스 이름의 기본값으로 Application 이름을 쓴다. 그대로 두면
Application 이름을 `traefik` 에서 `traefik-dev` 로 바꿀 때 릴리스 이름도 따라 바뀐다.

차트는 `Release.Name` 으로 라벨을 만들고, 그 라벨이 Deployment 의 `spec.selector` 에 들어간다.

```yaml
spec:
  selector:
    matchLabels:
      app.kubernetes.io/instance: traefik      # Release.Name 에서 온다
```

`spec.selector` 는 쿠버네티스가 불변으로 정한 필드다. 값이 바뀐 매니페스트를 apply 하면
`field is immutable` 로 거부되고, 반영하려면 Deployment 를 지웠다 다시 만들어야 한다.

`releaseName` 을 고정하면 Application 이름과 릴리스 이름이 분리된다.

| | 값 | 바꿔도 되나 |
|---|---|---|
| Application 이름 | `traefik-dev` | 된다 |
| Helm 릴리스 이름 | `traefik` | 바꾸면 파드가 재생성된다 |

이름 변경과 릴리스 고정은 같은 커밋에 있어야 한다. 나누면 그 사이에 대상 전부가 재생성된다.

## 8. 환경

| env | 클러스터 | 상태 |
|---|---|---|
| `dev` | 온프레미스 k3s | 활성 |
| `stg` | AWS EKS (아직 안 만듦) | 값은 다 채워져 있다. 배포 배선(Application·환경 축)만 없다 |

`prd` 는 만들지 않는다. 대상 클러스터가 생길 때 `envs/prd/` 를 신설한다.
아무도 참조하지 않는 폴더를 미리 두지 않는다.

환경을 하나 늘릴 때 손대는 곳은 이렇다.

```
argocd/applicationsets/*.yaml   환경 목록에 { env, server, registry } 한 줄
envs/<env>/                     그 환경의 값 파일 실물 (관측은 observability/ 하위)
argocd/applications/*.yaml      환경당 하나인 것 — netpol · kafka
argocd/projects/*.yaml          destinations 에 새 클러스터
.gitlab-ci.yml                  ACTIVE_ENVS 에 그 환경 이름
```

`ACTIVE_ENVS` 를 안 늘리면 새 환경이 CI 검증 밖으로 나간다.

**★ 환경이 갈리는 자리는 `envs/<env>/` 안의 파일뿐이다.** 그 밖 어디에도 환경 이름이
경로에 들어가지 않는다. 그래서 환경마다 달라지는 것은 전부 Helm 차트여야 한다 —
정적 매니페스트는 값을 받을 자리가 없다. NetworkPolicy 와 Kafka 가 2026-09-11 에
그 이유로 `manifests/` 에서 `charts/` 로 옮겨졌다.

**Application 이름의 접미사가 뜻하는 것** — `-dev` 가 붙어 있으면 다른 환경에도 짝이 생긴다.
접미사가 없는 것은 그 환경에만 있거나(`metallb-pool` · `public-guard` · `reset-app`)
환경 개념 밖이다(`root` · `argocd` · `argocd-image-updater` — 두 환경을 관리하는 평면이다).

## 부록 A. 배포 순서 — sync-wave

`argocd.argoproj.io/sync-wave` 애노테이션이 순서를 정한다. 숫자가 작은 것부터 적용되고,
같은 숫자는 동시에 간다. **앞 wave 의 리소스가 Healthy 가 될 때까지 다음 wave 를 시작하지 않는다.**

### 두 층위에서 각각 돈다

```
층위 1   root 가 argocd/ 를 sync 할 때
         AppProject 7 · Application 9 · ApplicationSet 5 가 이 순서로 만들어진다

층위 2   각 Application 이 자기 리소스를 sync 할 때
         manifests ApplicationSet 원소의 wave (-2 · -1 · 0) 가 여기에 해당한다
```

ApplicationSet 이 찍어낸 Application 은 그 AppSet 이 만들어진 뒤에 생긴다.
`argocd/applications/` 의 wave 와 AppSet 이 만든 Application 의 wave 는 같은 축이 아니다.

AppProject 의 wave 가 Application 보다 작은 것도 이 층위 때문이다. Application 이
`project: apps` 를 적었는데 그 프로젝트가 아직 없으면 그 Application 은 거부된다.

### 지금 순서

| wave | Application |
|---|---|
| -9 | `argocd` |
| -4 | `metallb` |
| -3 | `metallb-pool` |
| -2 | `traefik-dev` · `sealed-secrets-dev` |
| -1 | `kafka-dev` · `redis-dev` · `mysql` · `alerting` |
| 0 | `netpol-*` 3 · `rbac-dev` · `cert-issuers-dev` · `certificates-dev` · `minio` · `public-guard` · `reset-app` |
| 1 | `loki` · `mimir` · `tempo` · `grafana` · `alloy` · `kube-state-metrics` · `node-exporter` |
| 2 | `dashboards` · `argocd-image-updater` |
| 3 | `queue-dev` · `booking-dev` · `frontend-dev` |

순서의 근거는 의존이다.

| | 왜 그 자리인가 |
|---|---|
| `argocd` -9 | 제어면이 흔들리는 동안 나머지가 밀리지 않게 |
| `metallb` -4 → `metallb-pool` -3 → `traefik` -2 | 주소 할당기 · 주소 풀 CR · 그 주소를 받는 것 |
| `sealed-secrets` -2 | Secret 이 있어야 미들웨어가 암호를 읽는다 |
| `alerting` -1 | Grafana 파드에 마운트된다. 없으면 FailedMount 로 기동이 멈춘다 |
| `minio` 0 | loki · mimir · tempo (1) 가 여기에 저장한다 |
| `dashboards` 2 | sidecar 가 나중에 읽어도 된다. ConfigMap 은 그대로 남는다 |
| `argocd-image-updater` 2 | 폴링이라 감시 대상(3)보다 늦게 떠도 따라잡는다 |
| `reset-app` 0 | CronJob 은 대상이 없어도 만들어진다. 첫 판만 실패하고 다음 판에 성공한다 |
| 앱 3 | Redis · Kafka · MySQL · Secret 이 전부 있어야 한다 |

`alerting`(-1)과 `dashboards`(2)가 떨어져 있는 것은 실패 방식이 달라서다. 하나는 파드 기동을 막고
하나는 막지 않는다.

### 이 순서가 작동하는 때

빈 클러스터를 처음 세울 때와 전부 잃고 다시 세울 때뿐이다. 이미 떠 있는 클러스터에서는
변경이 하나씩 오므로 순서가 개입하지 않는다. **홈랩에서는 이 숫자들을 검증할 수 없다.**
stg 클러스터를 세우는 것이 이 순서를 실제로 확인하는 첫 기회다.

## 부록 B. 이미지 자동 갱신 — argocd-image-updater

GitLab 이 이 경로에서 세 역할을 한다.

| 역할 | 무엇 |
|---|---|
| CI | cgv-onprem 코드를 빌드해 이미지를 만든다 |
| 레지스트리 | 그 이미지가 저장되는 곳. 봇이 여기를 폴링한다 |
| git | cgv-infra 저장소. 봇이 여기에 커밋한다 |

```
1  cgv-onprem 의 main 브랜치에 머지 (trunk 하나. 환경 브랜치를 두지 않는다)
2  GitLab CI 가 이미지를 빌드해 레지스트리에 push
   태그 = main-<파이프라인 번호>-<커밋 해시>

3  argocd-image-updater 가 레지스트리를 폴링
     image-list          app={{.registry}}/{{.image}}
     allow-tags          regexp:^dev-[0-9]+-[0-9a-f]+$
     update-strategy     newest-build

4  새 태그를 찾으면 cgv-infra 에 커밋
     write-back-method   git
     write-back-target   helmvalues:/envs/{{.env}}/{{.name}}.yaml
     커밋 메시지          build: automatic update of <서비스>

5  main 이 바뀌었으므로 ArgoCD 가 sync 하고 새 이미지로 배포된다
```

**봇도 git 을 거친다.** 봇이 클러스터를 직접 고치면 저장소에 적힌 태그와 클러스터에 뜬 태그가
갈라지고, ArgoCD 가 그것을 드리프트로 보고 되돌린다.

애노테이션 셋에 이유가 붙는다.

| 애노테이션 | 값 | 왜 |
|---|---|---|
| `update-strategy` | `newest-build` | 태그가 semver 가 아니다. 문자열 비교로는 `dev-9` 가 `dev-15` 보다 크다 |
| `allow-tags` | `regexp:^dev-[0-9]+-[0-9a-f]+$` | MR 파이프라인 태그(`ci-pipeline-*`)와 손으로 올린 태그를 후보에서 뺀다 |
| `app.helm.image-name` | `imageUpdater.resolvedImage` | 봇은 이미지 이름 쓰기를 끌 수 없다. 템플릿이 읽지 않는 키로 돌려 렌더에서 분리했다 |

봇이 git 에 쓸 때 쓰는 자격은 ArgoCD 의 저장소 자격(`argocd-repo-cgv-infra`)이다.

## 부록 C. CI — 무엇을 커밋 시점으로 당기나

이 저장소에는 배포 파이프라인이 없다. 배포는 ArgoCD 가 한다. 그래서 잘못된 YAML 을
알려 주던 것이 클러스터였다 — ArgoCD 가 sync 에 실패하고 Application 이 빨개진 뒤에야 안다.
`.gitlab-ci.yml` 의 세 job 이 그 시점을 커밋으로 당긴다.

| job | 무엇을 보나 | 도구 | 잡는 것 |
|---|---|---|---|
| `lint:charts` | 차트 자체 | `helm lint` | 템플릿 문법 · `values.schema.json` 위반 |
| `template:render` | 차트 + 값 | `helm template` | 값이 안 맞아 렌더가 실패하는 것 |
| `validate:manifests` | 만들어진 결과물 | `kubeconform -strict` | 필드 오타 · 스키마에 없는 필드 · 타입 오류 |

대상이 다르다.

| job | `charts/` | `manifests/` |
|---|---|---|
| `lint:charts` | 본다 | — |
| `template:render` | 본다 | — |
| `validate:manifests` | 본다 (렌더 결과) | 본다 |

`manifests/` 는 렌더를 거치지 않으므로 앞 두 job 이 할 일이 없다. kubeconform 만 본다.

`-strict` 가 세 번째 job 의 존재 이유다. 필드 오타는 문법 오류가 아니라 문법적으로 성립하는
다른 필드라서, 이 옵션이 없으면 Helm 도 lint 도 kubeconform 도 통과시킨다.

`lint:charts` 는 차트 기본값만으로 돌릴 수 없다. `values.schema.json` 이 `resources` 를
required 로 걸고 그 값은 환경 층이 채우기 때문에, 기본값이 스키마를 못 지키는 것이 정상이다.
그래서 실제 배포와 같은 값 조합을 준다.

### kubeconform 이 확인하지 않는 것

kubeconform 은 클러스터에 접속하지 않는다. `schemas/` 의 스키마 파일과 대조할 뿐이다.

| | |
|---|---|
| 확인한다 | 필드 이름 · 타입 · 필수 필드 · apiVersion |
| 확인하지 않는다 | 이미지가 레지스트리에 있는지 |
| | 노드에 자리가 있는지 |
| | 참조하는 Secret · ConfigMap 이 있는지 |
| | admission webhook 이 거부할지 |
| | 기존 객체와 충돌하는지 (`spec.selector` 불변 위반 등) |

**CI 통과는 "확실히 틀린 것이 없다"이지 "배포된다"가 아니다.** 그것을 확인하려면
`kubectl apply --dry-run=server` 로 API 서버에 물어야 한다. CI 가 그것을 하지 않는 이유는
러너에 kubeconfig 가 없는 것과, 검증이 클러스터에 의존하면 클러스터가 죽었을 때
그것을 고치는 커밋조차 검증 없이 올려야 하기 때문이다.

CRD 스키마는 `schemas/` 에 커밋해 둔다. 갱신 절차와 함정은 `schemas/README.md` 에 있다.

## 부록 D. 아직 기준대로 되어 있지 않은 것

이 문서의 기준과 현재 코드가 어긋나는 지점이다.

1. **`manifests` ApplicationSet 의 환경 축이 이름까지만 걸려 있다** — 경로가 아직 환경별로
   안 갈렸다. stg 를 붙일 때 어떤 것이 환경별 경로를 필요로 하는지(봉인 키가 다른 `secrets`,
   도메인이 다른 `certificates`)가 정해지므로 그때 `path` 에도 `{{.env}}` 를 넣는다.
   개별 Application 9개는 온프레미스 전용이라 `destination.server` 가 리터럴인 것이 맞다.
2. **`charts/apps/<서비스>/` 에 차트가 없다** — `values.yaml` 하나뿐인데 `charts/` 아래 있다.
   값 전용 자리로 옮길지 정해야 한다.
3. **환경 축이 워크로드 넷에만 있다** — 관측 8종과 `manifests/` 아래 것들은 값으로 갈릴 자리가 없다.
   `kafka` 는 브로커 수가 CR 에 있어 환경마다 못 바꾼다. 차트로 만들면 `data` AppSet 으로 옮긴다.
4. **`clusterResourceWhitelist: []` 가 `data` 프로젝트에서 검증되지 않았다** — 미들웨어가
   cluster 범위 리소스를 안 만든다는 판단으로 닫았다. 틀렸으면 ArgoCD 가
   `resource not permitted in project` 로 실패하므로 조용히 넘어가지는 않는다.
5. **`platform` 프로젝트가 관측과 진입을 함께 담는다** — 갈랐을 때 `clusterResourceWhitelist` 는
   양쪽 다 `*` 로 같지만 `sourceRepos`(4 / 2)와 `destinations`(2 / 2)는 갈린다.
   지금은 traefik Application 이 `observability` 네임스페이스에, grafana Application 이
   `metallb-system` 에 객체를 만들 수 있다. 관측을 다른 사람이 맡게 되면 그때 가른다.
6. **업스트림 차트 소스가 A 와 B 로 섞여 있다** — 목표는 C 통일이고 실행은 EKS 사이클 뒤다.
7. **booking 에 스키마 마이그레이션 도구가 없다** — `charts/apps/cgv-app` 의 `migration-job.yaml` 은
   PreSync Job 으로 마이그레이션을 1회 적용하는 자리인데, booking 에 Flyway 가 없어
   `migration.enabled=false` 이고 `DDL_AUTO=update` 로 단일 replica 를 쓴다.
   여러 replica 로 띄우면 파드들이 동시에 `CREATE TABLE` 을 시도한다.
   수정 대상은 cgv-onprem/booking 이다.
